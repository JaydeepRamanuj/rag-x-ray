# Lesson 14: Process log

The decisions made while building RAG X-Ray, what broke, and why. One entry per phase, written when the phase ends.

## Phase 0: Foundation (31 Oct 2026)

**What was built:** a Next.js 16 app shell with a sidebar, placeholder pages for every module, the seven-table schema in Neon with pgvector, `lib/config.ts`, this Learn page, and [`/api/health`](/api/health).

### Decisions

- **Model IDs were checked against the providers' docs before writing config, and two of them had already changed.** Groq shut down `llama-3.1-8b-instant` on 16 Aug 2026, so the fast comparison model is now `openai/gpt-oss-20b`, which Groq recommends as its replacement. On Gemini, the newest stable Flash-Lite is `gemini-3.5-flash-lite` and the judge is `gemini-3.8-flash`. The lesson: a spec written weeks ago can already be out of date, so model IDs belong in one file (`lib/config.ts`), not scattered through the code.
- **Neon's HTTP driver for the app, a direct connection for migrations.** Each query from `@neondatabase/serverless` is a single `fetch`, so there's no connection pool to keep warm in a serverless function. Migrations use the direct (non-`-pooler`) host because PgBouncer's transaction pooling doesn't handle multi-statement DDL well.
- **pgvector gets its own migration.** drizzle-kit generates tables but not `CREATE EXTENSION`, so `drizzle/0000_enable_pgvector.sql` is a hand-written migration that runs before any table uses the `vector` type.
- **One vector column per embedding model** (`embedding` at 768 dims, `embedding_local` at 384). Vectors from different models live in different spaces. Comparing them is meaningless, so they should never share a column.
- **`tsv` is a generated column.** Postgres recomputes `to_tsvector('english', content)` on every write, so keyword search can't drift out of sync with the text.
- **`run_chunks` got a composite primary key** of (run, chunk, method). The spec didn't name one, but without it the same chunk could be recorded twice for the same method.

### What broke

- **pnpm 12 refused to install** because esbuild's install script was blocked by default. The fix was allowing it explicitly in `pnpm-workspace.yaml`. Newer package managers treat install scripts as a supply-chain risk and make you opt in to each one.
- **Next.js 16 with Cache Components rejects `export const runtime = 'nodejs'`.** Node is already the default runtime. Instead, the health route calls `await connection()`, which stops Next from prerendering it at build time and serving a frozen "healthy" answer forever.

### What to notice

Open [`/api/health`](/api/health) twice, a few seconds apart, after the app has been idle for more than five minutes. The first `database.ms` is much higher than the second because Neon's compute was asleep. That's the cold start.

## Phase 1: Raw LLM call and streaming (31 Oct 2026)

**What was built:** a provider adapter for Gemini and Groq written with plain `fetch`, a hand-written SSE parser and encoder, `/api/chat` streaming its own SSE events, the [Chat](/chat) page with Stop and live stats, and the streaming debugger at `/runs/[id]/stream`. Every call is saved to `runs`.

### Decisions

- **Probe before coding.** The docs left gaps: where streamed usage arrives, what the thinking setting is called, how a 429 looks. One tiny live call to each provider answered them. Gemini repeats a running `usageMetadata` total on every chunk; Groq sends `usage` once, just before `[DONE]`, and only if you ask with `stream_options.include_usage`.
- **Thinking is set per model, at its floor.** All four chat models are reasoning models. Gemini 3.5 Flash-Lite accepts `thinkingLevel: "minimal"`, Gemini 3.8 Flash rejects it with a 400 and needs `"low"`, and GPT-OSS takes `reasoning_effort: "low"`. Each model's value lives in `lib/config.ts`.
- **`outputTokens` means "billed output".** Gemini counts thinking separately from the answer; Groq folds it in. The adapter normalises to answer + thinking, with thinking also reported on its own.
- **The run id is created in the route, not the database**, so the browser gets it in the first event without waiting on a possibly cold Neon. The run is written with `after()`, which runs once the response finishes, including when the client disconnects.
- **`runs` gained `status` and `error` columns.** A stopped run keeps its partial answer and whatever usage arrived, so you can see what tokens you paid for. Migration `0002_runs_status`.
- **Retries stop before streaming starts.** Once tokens reach the user, replaying the request would duplicate them. A `retry-after` longer than 30 s fails fast, because it usually means a daily quota is gone.
- **One SSE parser for both directions.** The server reads Gemini and Groq with the same `readSse()` that the browser uses to read us.

### What broke

- **Gemini 3.8 Flash returned 503 "high demand"** during the first probe. That's why 5xx is retried as well as 429.
- **Next 16 rejected `dynamicParams` again**, this time indirectly: the stream page reads the database, so it renders inside `<Suspense>` to keep the rest of the page prerenderable.
- **The React Compiler lint rule flagged reading a ref during render** (the stream start time). It became state.
- **A wide table stretched the whole page.** The main column is a flex child, and flex children won't shrink below their content's width unless told to with `min-w-0`. The fix is one class on the layout; lesson tables also scroll on their own now.
- **`next/link` inside `mdx-components.tsx` broke lessons in dev.** Lessons load through a dynamic import, and Next's dev-time navigation check couldn't resolve the Link module along that path. Plain `<a>` tags do the job for lesson links.
- **The debugger first showed upstream frames double-escaped** (JSON inside our JSON envelope). It now shows each frame exactly as the provider sent it.

### What to notice

- In the debugger with **slow network** on, the server's work ends at about 1.6 s but the browser is still reading at 11 s. One read can deliver twenty events at once once the client falls behind. That's back-pressure.
- GPT-OSS bills about 80 input tokens for a five-word question; Gemini bills about 7. The difference is GPT-OSS's chat template, covered in Lesson 2.

## Phase 2: Ingestion and basic RAG (31 Oct 2026)

**What was built:** a [Documents](/documents) page that uploads `.md`, `.txt` and `.pdf` files. Each file is extracted, cleaned, split into ~400-token chunks with 40 tokens of overlap, embedded in batches with Gemini, and stored in pgvector. Embeddings are cached in Upstash Redis. In [Chat](/chat), **Use documents** retrieves the top-k chunks for each question and the answer cites them as [1], [2], with the sources listed underneath.

### Decisions

- **Re-uploads replace, they don't duplicate.** `documents.content_hash` is a sha256 of the extracted text. Uploading the same content again re-embeds it (from the cache) and swaps the old copy out, but only after the new one is ready, so a failed upload never leaves you with neither.
- **Everything for one document is written in one transaction.** The Neon HTTP driver can't hold a transaction open across awaits, but `db.batch()` sends all the statements together. IDs are generated in the app so later statements can reference earlier rows.
- **Sources go in the last user message, not the system prompt.** They belong to that question only. Earlier turns are re-sent without their sources, so the prompt doesn't grow by top-k chunks every turn.
- **Queries are cached too**, with their own task type in the key. Asking the same question again skips the embedding call (about 1.1 s down to about 0.16 s).
- **A shared password guards uploads and deletes.** With `APP_PASSWORD` unset, local dev is open and production refuses uploads. The comparison is constant-time.
- **Answers render as Markdown**, with citations rewritten into links that open the matching source.

### What broke

- **The documented embedding config was silently ignored.** Google's docs mark the top-level `taskType` and `outputDimensionality` fields deprecated in favour of `embedContentConfig`. Sent that way, the API returned 3,072-dim vectors with no error. The old fields work, so the code uses them, with a comment explaining why.
- **Truncated embeddings aren't unit length.** The 768-dim vectors came back with a length of about 0.59. Cosine search doesn't care, but anything that treats the dot product as similarity would be wrong, so vectors are normalised before storage.
- **No token usage from the embeddings API**, despite the docs. Embedding tokens are estimated locally.
- **Prettier reformatting files under a running dev server** set off a reload loop that froze the browser pane. Formatting now runs with the dev server stopped.

### What to notice

- `EXPLAIN ANALYZE` on the 18-chunk table shows a sequential scan (0.16 ms) rather than the HNSW index (10 ms when forced). The planner is right: indexes pay off at thousands of rows, not dozens. The app's ~500 ms "search" time is almost entirely network latency to Neon.
- Relevant and loosely related chunks score within about 0.1 of each other (0.77 vs 0.65). The ranking matters, not the absolute score.

## Phase 3: Prompt inspector and token ledger (31 Oct 2026)

**What was built:** an **Inspect** button on every chat answer, opening the prompt inspector at `/runs/[id]/prompt`. It shows the exact messages sent, split into system prompt, history, framing, numbered sources and question, with a token bar per part, and it can count each part with the model's own tokenizer. Edit the rules, drop sources or switch model, then **Re-run** to compare the answers side by side. The [ledger](/ledger) lists every run's tokens, latency and paid-tier cost, charts daily usage against each model's free quota, and re-prices any run with a what-if panel. Lessons [9](/learn/prompt-construction) and [11](/learn/caching-and-cost).

### Decisions

- **Saved prompts are taken apart, not re-derived.** `final_prompt` is the source of truth. The inspector rebuilds the sources from `run_chunks` and uses them only if they reproduce the saved text exactly. If the chunks have gone (document deleted or re-uploaded), it parses the numbered blocks back out of the text instead. Either way, it shows what was sent rather than what the code would send today.
- **Estimates per part, the provider's number for the total.** Each part gets a local o200k estimate; the bill comes from `runs.input_tokens`. The gap between them is shown, not hidden: for Gemini it's almost all tokenizer (its per-part counts summed to 2,263 against 2,260 billed), while for GPT-OSS it's mostly chat template.
- **Token counting stays on the server.** The o200k vocabulary is too big to ship to the browser, so estimates are made when the page renders and when the ledger loads.
- **A re-run is a normal run with a parent.** It goes through `/api/chat` in raw mode with `parentRunId`, so it is timed, saved and priced like any other run, and shows in the ledger. Its chunks are saved with `used_in_prompt` true or false, which is what that column was waiting for since Phase 0.
- **Migration `0004_ledger_usage`:** a `reasoning_tokens` column on `runs` (thinking was only inside `output_tokens` before), and an `ingest_usage` table so upload embeddings count towards the daily chart. Upload usage is logged even if storing the document then fails, and kept when the document is deleted (`ON DELETE SET NULL`), because the quota was used either way.
- **Days are Pacific days.** Gemini's daily quota resets at midnight Pacific, so the chart buckets with `AT TIME ZONE 'America/Los_Angeles'` in SQL, and the axis fills in empty days in JS.
- **Gemini's free limits come from Jd's AI Studio** (Flash-Lite: 15 RPM, 250K TPM, 500 RPD). Google no longer publishes them.
- **The what-if holds output constant** and scales input by the ratio each run actually showed between the provider's count and our estimate. Switching provider drops that ratio and marks the result approximate.

### What broke

- **The disk filled up mid-phase**, and pnpm couldn't install Recharts. Then shadcn's own `pnpm add` used a different store path than the existing `node_modules`. The fix was installing Recharts directly with the project's store (`--store-dir`), then letting shadcn write only `chart.tsx`.
- **Recharts drew nothing in a hidden browser pane.** React 19 reveals streamed Suspense content on an animation frame, and a background tab doesn't get any, so the ledger stayed on "Loading runs…" with its HTML already delivered. Not an app bug, but worth knowing when a page "hangs" only while you're not looking.
- **The React Compiler lint rule rejected `Math.random()` in render** (a fallback list key), and a counter mutated inside `map()` during render. Both became pure derivations.
- **Clicking Inspect the instant an answer finished could beat the database write**, since runs are saved with `after()`. The inspector page retries the lookup briefly before giving up.

### What to notice

- 95% of a top-5 RAG prompt is sources. Dropping the two lowest-ranked of five took a run from 2,260 to 1,347 input tokens with the same answer, because it only cited [1] and [3].
- Gemini's implicit cache works on the free tier, but only after about 20 s and only on a prefix (4,071 of 6,217 tokens). None of the RAG runs so far had a cached token: the stable prefix is under 100 tokens.
- Output costs 8.3× input on Flash-Lite, so across 22 runs the bill was split about 49/51 between input and output, even though there was 8× more input.
